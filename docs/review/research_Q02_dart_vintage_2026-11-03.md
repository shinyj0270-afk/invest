# Q02 조사 — DART 최초·정정공시의 공개시각과 재무 셀 빈티지 보존

작성일: 2026-11-03. 조사 주체: Claude Code(직접 조사). 질문은 [research_questions.md](research_questions.md) Q02. 선행 조사: [Q01](research_Q01_krx_pit_2026-11-03.md).
이 문서는 조사 기록이며 지표 도입·공급자 계약·코드 변경의 승인이 아니다. 법률 자문이 아니다.

## 조사 방법과 증거 등급

- DART·OpenDART·KIND 페이지를 2026-11-03에 브라우저로 직접 열어 본문을 읽었다. **[직접]**
- 웹 검색 요약만 본 항목은 **[검색요약]**이다. 원문을 열지 않았으므로 낮은 등급이다.
- 「전자문서제출요령」 개정 파일(hwp)은 다운로드가 필요해 열지 않았다. 해당 접수시간은 **확인 불가**로 둔다.
- API 인증키가 필요한 호출은 하지 않았다. 실제 응답 값으로 검증한 사항은 없다.

## 연구 결과

1. **공개 "시각"은 OpenDART로 얻을 수 없다.** 접수일자만 있다(G1, G2). 시각은 KIND "오늘의공시"에만 있고, 이 화면은 최근 4영업일 탭만 보인다(G9). 과거 시각 보존 여부는 확인하지 못했다.
2. **같은 날 장 마감 후(예: 18시) 접수와 장중 접수를 OpenDART 날짜만으로 구분할 수 없다.** 접수시간 규정이 2024-04-25에 개정됐으나 내용은 열지 못했다(G10).
3. **재무 값의 "빈티지"를 API로 직접 고정할 수 있는 경로는 두 개다.**
   - 경로 A: 공시검색(`last_reprt_at=N`)으로 정정 포함 전체 접수본의 `rcept_no`·`rcept_dt`를 수집하고, 접수본마다 XBRL 원본(G5)을 받는다. 접수본 단위 빈티지가 생긴다.
   - 경로 B: 재무 API(G4)는 접수번호를 지정할 수 없다. 응답의 `rcept_no`를 기록하면 "어느 접수본 값이었는지"는 사후에 알 수 있으나, 같은 요청이 시점에 따라 다른 접수본을 줄 수 있는지는 확인하지 못했다.
4. **정정본이 원본을 가리키는 필드가 없다**(G3). 원본과 정정본의 연결은 corp_code·보고서명·기간으로 구성해야 하며, 이 매칭의 정확도는 확인하지 못했다.
5. **일괄다운로드는 정정 후 값으로 바뀔 수 있고, 생성일자가 바뀐다**(G7). 수집 시점을 같이 저장하지 않으면 과거 시점에 무엇이 보였는지 복원할 수 없다.
6. **구조화 재무는 2015년 이후다**(G4, G7, G8). 2008·2020·2022 가운데 2008은 OpenDART 재무 API 범위 밖이다. DART 공시 자체는 1999-04 이후 있다는 연혁이 검색요약으로 확인된다(Q01 F16).

## 우리 시스템에 대한 해석 [AI 해석]

- "공개일 미확인 공급자 보충값"은 현재 화면과 과거 검증에서 같은 열에 섞이면 안 된다. 최소한 `rcept_dt`가 공식 접수일인 값, 공급자값이라 접수일이 미확인인 값, 임의 지연으로 추정한 값을 서로 다른 상태로 저장해야 한다. 이 3분류는 제 제안이며 외부 근거는 없다.
- 시각을 알 수 없으면 가장 보수적인 사용 가능일은 "접수일의 다음 영업일"이다. 이것도 제안이며, 장중 접수분까지 하루 늦춰 쓰게 되는 비용이 있다.
- 임의 고정 지연(예: 분기말+45일)은 법정 기한(G11, G12)과 실제 접수일이 다르다는 점에서 부정확하다. 법정 기한은 상한일 뿐 실제 접수일의 대리변수가 아니다. 기한 연장 신고(제165조, 검색요약)나 조기 제출도 있다.
- 정정공시 때문에 같은 (회사, 기간)에 값이 여러 개 생길 수 있다. 과거 검증에는 "그 시점에 이미 접수된 최신 접수본"만 써야 한다.

## 아직 검증할 가설

- H1: 재무 API(G4)는 항상 최신 정정본의 값을 반환한다.
- H2: 정정본의 `report_nm`에 붙는 [기재정정] 표기와 `rcept_dt`만으로 원본과의 순서를 복원할 수 있다.
- H3: KIND 공시 시각(HH:MM)은 과거 일자에서도 조회되며, DART `rcept_dt`와 같은 날짜로 일치한다.
- H4: 장 마감 후 접수된 정기보고서의 비율이 무시할 수 없는 수준이다(접수 시각이 없어 현재는 측정 불가).

## 채택 전 최소 데이터·테스트

1. T1 (H3): 임의 대형주 5곳의 최근 분기 보고서에 대해 KIND 시각과 DART 접수일자를 대조한다. 과거 일자 조회 가능 범위도 기록한다.
2. T2 (H1·H2): 정정공시가 있었던 기업 3곳을 골라, 사용자가 발급한 OpenDART 키로 공시검색(전체 접수본)과 재무 API를 호출해 접수번호별 값 차이를 비교한다. 키 발급은 사용자 행위다.
3. T3: XBRL 원본 API(G5)로 원본과 정정본을 각각 받아 같은 계정의 값 차이를 확인한다.
4. T4: 「전자문서제출요령」 전문(hwp)을 사용자가 열어 접수시간을 확인하거나, DART 전자공시팀(02-3145-8612, G10 페이지 기재)에 문의한다.
5. T5: 공급자 보충값(예: 인포맥스)에 접수일자가 있는지, 없다면 어느 공식 날짜와 매칭할지 필드 단위로 점검한다. 이 시스템의 실제 공급자 필드는 이번에 읽지 않았다.

## 필요 입력 필드 (빈티지 계약 제안)

접수본 식별: rcept_no·rcept_dt·report_nm(정정 태그 포함)·corp_code·stock_code·보고서 코드·사업연도. 값: 계정ID·계정명·금액·통화·개별/연결(OFS/CFS)·재무제표 구분·당기/전기 구분·결산기준일. 시점 메타: 수집 시각(우리 측)·출처(API/XBRL/일괄다운로드/공급자)·일괄다운로드 생성일자·날짜 신뢰 상태(공식 접수일 / 공급자 미확인 / 추정 지연)·사용 가능일 산정 규칙 버전.

## 기존 구현과의 차이와 도입하지 않을 이유

- 기존 시스템의 날짜·접수일 처리는 이번에 읽지 않았다([redteam](redteam_2026-11-03.md) R01/R02 참조). 차이 분석은 해당 코드를 읽는 별도 작업이다.
- 도입 보류 이유: ①접수 시각 데이터가 공식 API에 없음, ②정정본→원본 연결 필드 없음, ③재무 API의 버전 선택 불가(G4), ④접수시간 규정 미열람. T1~T4 전에는 사용 가능일 규칙을 코드에 반영하지 않는다.
