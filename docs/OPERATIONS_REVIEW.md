사용자 결정(2026-10-19): Orca 기반 현재 작업 방식(원본 main + Orca 작업 워크트리 하나 + 작업 단위 세션 + Claude/Codex/ChatGPT 분담)이 계속 최선인지 정기적으로 점검한다. 예약은 두지 않는다. 매월 첫 INVESTMENT START에서 이번 달 기록이 없으면 AI가 "운영 점검 시기"라고 알리고, 점검은 사용자가 원할 때 진행한다.

## 역할

- 판단·대안 선택: ChatGPT 주도(공통 역할 규칙), 최종 결정은 사용자.
- 수치 수집: 그 시점 START한 Claude/Codex가 Git 로그·CURRENT_HANDOFF·PROJECT_STATE·로컬 검증 기록에서 아래 항목을 읽기 전용으로 정리한다. 추정치는 추정으로 표시한다.
- 점검 결과로 규칙·도구를 바꾸면 기존 MERGE/CLOSE 절차를 따른다. 점검만으로 설정·예약·워크트리를 바꾸지 않는다.

## 이번 체계 도입 당시 관찰(2026-10-19, Claude 세션)

- 한 세션이 길어져 사용량 사유로 Codex에 교대했다.
- 코드 반영마다 입력 보관 확인 → 안전 재시작 → push가 반복됐다.

## 2026-10 운영 점검 · 2026-10-22

### 범위와 근거

- 사용자 요청 “운영 점검하자”에 따른 점검. 기준 main/Orca invest 3580f58059338c54f82bf5a02d04c403052e6f8a. 현재 회사 work에서 Git 이력·PROJECT_STATE·CURRENT_HANDOFF·이 문서 및 회사의 로컬 검증 파일 목록을 읽었다. 집의 개인 로그·DB·원자료·검증 영수증은 수신하지 않았으며 집 결과는 Git 인계의 SOURCE_RECORDED다.
- 기간은 2026-10-19 00:00 KST부터 2026-10-22 00:00 KST 직전까지의 현재 HEAD에서 도달 가능한 Git 이력이다. `git log --since=2026-10-19T00:00:00+09:00 --until=2026-10-22T00:00:00+09:00` 및 각 커밋 `git diff-tree --no-commit-id --name-only -r`로 직접 집계했다. 날짜 표시는 Git 작성일 기준이며 세션 경계와 같지 않다.
- 총57커밋(작성일별19일32·20일13·21일12), 변경 경로가 전부 .md인 커밋32, 그 외25. 문서만 변경한 커밋에도 필요한 검증·운영 결정이 포함되므로 이 수치로 낭비율·기능 수·세션 수·절감률을 계산하지 않는다. 공급자 사용량·비용·실제 AI 세션 수는 미확인이다.
- 현재 CURRENT_HANDOFF는54줄/14,663바이트다. 줄 수가 짧아도 한 줄에 과거 완료 이력이 누적되어 읽을 내용이 많다. 회사 validation/current에서19일 이후 수정된 파일 목록은 스크린샷1개만 확인됐다. 다른 검증 기록이 전체 PC/다른 폴더에 없다는 뜻이 아니며, 이 PC 파일만으로 집 검사나 전체 실패 횟수를 검증하지 않는다.

### 대안 비교와 제안 (점검 당시 제안; 아래 채택 기록 참조)

1. **우선 제안: Orca·작업 워크트리 하나·작업 단위 세션을 유지하고 인계/반영 단위를 개선한다.** 현재 구체적 부담은 도구 독점 기능보다 중복 기록·상태 불일치·반영 횟수에 있다. 단, 이는 최근 기록에 근거한 판단이며 다른 실행 환경과 같은 과제로 비교한 성능 결과는 아니다.
2. 일반 git worktree+터미널로 옮기는 대안은 현재 미채택. 비교 실험 없이 OAuth/권한 문제가 모두 해결되거나 비용이 줄어든다고 단정할 수 없고 기존 main 격리·안전 재시작·PC별 데이터 인계 의무는 그대로 남는다.
3. 담당 AI를 더 자주 전환하는 대안도 현재 미채택. Codex가 구현·관련 검증을 끝내고 판단 쟁점이 있을 때만 ChatGPT/Claude 검토로 넘기는 현 분담을 유지하는 쪽을 제안한다. 실제 다른 모델 호출이나 설정 전환은 실행하지 않았다.

사용자 선택을 위한 구체적 개선안:

- 다음 CLOSE에서 CURRENT_HANDOFF를 누적 완료 목록 대신 이번 완료·현재 pending·다음 한 작업으로 교체한다. 필수 인계 필드는 유지하고 날짜 의존적인 “내일”은 실제 날짜/자료 전달 조건으로 쓴다. 이전 완료 근거는 PROJECT_STATE/Git 이력으로 연결한다.
- 사용자가 중간 반영을 요청하지 않은 같은 목표의 연속 변경은 각 관련 검증 후 한 번 MERGE/CLOSE 반영하는 방식을 제안한다. 입력 보관 확인·안전 재시작·필수 검증은 생략하지 않는다.
- 결과 단일 발행PC=home, 개발 역할 work Primary/home Secondary를 구분해 START에서 표시한다. Git 수신/운영 실행/결과 발행/다른 PC 수신은 각각 확인한 단계만 보고한다.
- 다음 점검에는 기존 문서 안에 작업별 반영/재시작 횟수·사용량 때문에 교대한 여부·재질문/재작업 발생만 짧게 남기면 비교가 쉬워진다. 새 자동수집·예약·전체 세션 공유는 추가하지 않는다.
